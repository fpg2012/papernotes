## 1. TLDR

- **领域**: VLM 空间推理 (Spatial Reasoning)
- **任务**: 让 VLM 在多视图图像和视频中理解空间关系——方向判断、距离估计、视角变换等
- **问题**: 多视图/视频中的空间线索稀疏、分散在冗余帧里。VLM 直接看图容易"淹没"在冗余视觉信息中。即使给 VLM 加上 3D 重建工具，无约束的 tool use 也很脆弱——VLM 可能用错工具、跳过关键变换、误用中间结果
- **核心贡献**: 用前馈式 3D 重建构建显式点云空间记忆 + DSL 文法约束 VLM 如何查询/变换/渲染记忆，把空间推理变成受验证的结构化程序执行

## 3. 相关工作背景

论文站在三条研究线交叉点上:

- **Spatial Memory（空间记忆）**: 认知科学认为结构化记忆支持视角变换和导航。Reasmory 的不同在于推理时构建显式 3D 点云记忆 + 语义实例标注 + 受约束的程序化操作接口
- **3D Reconstruction + Spatial VLMs**: NeRF/3DGS 等提供了重建能力，但直接暴露给 VLM 当工具用不稳定。Reasmory 把重建结果变成可查询/变换/渲染的空间记忆
- **Programmatic Tool Use & DSLs**: VISPROG、ViperGPT 等用程序组合视觉模块。Reasmory 引入带 AST 验证的 DSL——不仅生成程序，还检查语法、工具合法性、依赖一致性、视角状态一致性。未通过验证的程序被拒绝并重新生成

## 4. 核心方法

### 4.1 问题形式化

给定多视图图像或视频帧序列 $ \{V_1, V_2, ..., V_n\} $ 和一个空间推理问题 $ q $:

1. 用前馈式 3D 重建器 $ \mathcal{R} $ 重建深度图 $ \{D_1, ..., D_n\} $、相机位姿 $ \{T_1, ..., T_n\} $、内参 $ K $
2. 像素反投到 3D: $ \mathbf{x} = T_i^{-1}(D_i(u,v) \cdot K^{-1}[u, v, 1]^{\mathsf{T}}) $，得到带 RGB 颜色的稠密点云
3. 用语义分割模型给点云添加语义实例标签
4. 生成、验证、执行 DSL 程序回答 $ q $

### 4.2 架构详解（含具体示例）

先扔一个具体问题贯穿全程，方便理解每一步在干什么：

> **示例问题**：\"If I'm standing at the same spot and facing the same direction as shown in image 1, then I turn right and move forward, will I get closer to the pink plush toy and headboard?\"
> **输入**：4 张不同角度的卧室照片（image 1~4），其中 image 1 是第一人称视角拍摄

下面看系统从零到最终答案的全过程。

---

#### 第一步：构建 3D 空间记忆

**做什么**：把 4 张 2D 照片变成一个 3D 点云

1. 4 张照片 $ V_1 \sim V_4 $ 输入 Pi3（前馈式 3D 重建器，一次前向传播即可）：
   - 输出每张图的稠密深度图 $ D_1 \sim D_4 $（每个像素的深度值）
   - 输出每张图的相机位姿 $ T_1 \sim T_4 $（相机在 3D 空间中的位置和朝向）
   - 输出相机内参 $ K $（焦距、主点等）

2. 对每张图的每个像素 $ (u,v) $，反投影到 3D 空间：
   $$ \mathbf{x} = T_i^{-1}\big(D_i(u,v) \cdot K^{-1}[u, v, 1]^{\mathsf{T}}\big) $$
   每个像素变成一个带 RGB 颜色的 3D 点，4 张图合成一个**彩色稠密点云**

3. 坐标对齐：重力方向（地板→天花板）对齐到 y 轴，墙面方向对齐到 x/z 轴

**产出**：一个包含整个房间几何结构的彩色 3D 点云 $ \mathcal{X} $，以及每张图的相机位置 $ T_i $

> 以卧室为例：这一步产出了床、头板、粉色毛绒玩具等所有物体在 3D 空间中的位置和形状的几何表示。

---

#### 第二步：语义增强——给点云里的物体打标签

**做什么**：在点云上标注出哪些是床、哪些是毛绒玩具、哪些是头板

**怎么做的**（Algorithm 1, P.5）：

问题里提到的物体需要在 3D 点云里被识别出来，才能让 VLM 后续查询它们的位置。

1. 对每个物体类别（如"plush toy"），用 SAM3（开放词汇分割）在 4 张原始图片上都跑一遍，得到该类的候选 mask
2. 对每个候选 mask，利用第 1 步重建的 3D 几何，把 2D mask 提升（lift）到 3D——算出它占据哪些 3D 网格单元
3. **跨视图一致性评分**：同一物理物体在不同视角下的 proposal 应该占据一致的 3D 区域。打分高的说明是同一物体
4. 在类别内构建一致性图（graph），贪心合并互相一致的 proposal（每个视角最多选一个 mask）

**产出**：带类别标签、3D 中心坐标、关联 3D 点的物体实例列表，例如：
- `plush_toy_1`: center=(1.2, 0.3, -0.8)，关联 342 个 3D 点
- `headboard_1`: center=(0.0, 0.8, -2.1)，关联 1567 个 3D 点

现在 VLM 可以用 `query_3d_object_location("plush toy")` 获取毛绒玩具的精确 3D 位置了。

---

#### 第三步：问题分解（Question Decomposition）

**做什么**：把自然语言问题拆成结构化的推理步骤

**怎么做的**（Algorithm 2, P.5）：

输入问题被分解器拆成三个阶段：

1. **选择参考视角**：根据问题确定初始相机位置。示例问题提到"same spot and facing same direction as image 1"，所以初始视角就是 image 1 的相机 $ V_{\text{ini}} = \text{camera}_1 $
2. **视角精炼**：按问题中描述的动作更新视角。"turn right" → 绕 y 轴旋转 90°；"move forward" → 沿当前朝向平移一段距离
3. **实体比较**：应用比较函数 $ f $ 回答问题。$ f $ 可以是 direction()、distance()、visibility()、count() 等

**具体到示例问题**，分解结果（Table 1 第 4 行, P.7）：

> Reference: $ V_{\text{ini}} = \text{camera}_1 $ → Refinement: rotate(right), move(forward) → Comparison: direction(ego, plush toy)

意思是：先把相机放到 image 1 的位置 → 向右转 90° → 向前走一步 → 然后判断"我"和毛绒玩具之间的方向关系（是更近了还是更远了）

其他示例（Table 1）：
- "How many tables are in the room?" → 无需参考视角 → 无需变换 → count(table) + BEV 俯视图
- "What is behind me if I stand at the same spot as image 3?" → 视角放到 camera₃ → rotate(back) → visibility(ego, object) + 渲染新视角的 RGB

---

#### 第四步：DSL 程序规划——把分解翻译成可执行代码

**做什么**：把第三步的分解翻译成一个实际的 Python 程序（但只能用允许的 DSL 原语）

**可用原语**（Table 2a, P.7）：

| 类别 | 操作 | 语义 |
|------|------|------|
| Memory Construction | `build_static_memory()` | 加载/构建 3D 空间记忆 |
| | `build_dynamic_memory()` | 构建动态场景记忆（视频） |
| Memory Query | `query_camera_pose(name)` | 获取某张图的相机位置 |
| | `query_3d_object_location(name)` | 获取某物体的 3D 中心坐标 |
| Memory Transformation | `set_viewpoint(pose)` | 把当前视角设到指定位置 |
| | `step_camera(distance)` | 沿当前朝向平移相机 |
| | `turn_camera(angle)` | 旋转相机（left/right/back） |
| Rendering | `render_egocentric()` | 渲染当前视角的 RGB 图 |
| | `render_semantic_bev()` | 渲染俯视语义图 |
| | `render_rgb_bev()` | 渲染俯视 RGB 图 |

**不同阶段允许不同的原语**（Table 2b）：
- 参考视角选择阶段：只能用 Memory Construction + Memory Query
- 视角精炼阶段：可以用 Memory Query + Memory Transformation + Rendering
- 实体比较阶段：只能用 Memory Query + Rendering

**示例程序**（对应示例问题）：

```python
# 阶段 1：参考视角选择
mem = build_static_memory()                                     # 加载 3D 点云
cam1_pose = query_camera_pose("image_1")                        # 获取 image 1 的相机位置

# 阶段 2：视角精炼
set_viewpoint(cam1_pose)                                        # 把视角设到 image 1 的位置
turn_camera("right")                                            # 向右转 90°
step_camera(1.0)                                                # 向前走 1 米
view = render_egocentric()                                     # 渲染新视角下的画面

# 阶段 3：实体比较
plush_toy_pos = query_3d_object_location("plush toy")          # 获取毛绒玩具的 3D 位置
result = direction(ego, plush_toy_pos)                         # 判断方向关系
# result: "closer" or "farther"
```

---

#### 第五步：程序验证（AST Compiler）

**做什么**：在真正执行之前，检查生成的程序有没有问题

**检查 6 类规则**（Table 3, P.7）：

| 规则类别 | 示例规则 | 检查什么 |
|----------|----------|----------|
| 1. 程序语法 | 受限 Python 子集 | 禁止装饰器、可变参数等 |
| 2. 工具白名单 | 只允许 DSL 原语 | 不能调用 `os.system()` 等 |
| 3. 依赖一致性 | define-before-use | 变量必须在使用前定义 |
| 4. 视角状态一致性 | 旧查询结果失效 | 视角变换后必须重新查询 |
| 5. 执行纪律 | 不允许悬空的移动 | 每个相机移动后必须跟一个 render |
| 6. 计划一致性 | 移动方向匹配分解 | 实际参数必须与分解结果一致 |

**具体示例**：如果 planner 生成的程序在 turn_camera 之后没有 render 就去做别的事，编译器会在第 5 条规则（执行纪律）上拒绝这个程序。类似地，如果视角变换后使用旧的 query 结果（第 4 条），或者移动方向是 left 但分解要求 right（第 6 条），都会被拒绝并返回编译器错误，planner 根据错误反馈重试。

**效果**（Table 9b, P.12）：GPT-5-mini 的 pass@1 = 82.6%，pass@3 = 95.3%；Gemini-3-flash pass@3 = **100%**。说明绝大多数程序在前 3 次尝试内就能通过验证。

---

#### 第六步：执行 + 推理

**做什么**：执行验证通过的程序，把结果送给 VLM 得出最终答案

1. **Execution Engine** 逐行运行程序：构建点云、查询位置、变换视角、渲染新画面
2. 所有执行结果（渲染图、查询的坐标、计算结果）拼到上下文里
3. **Reasoner**（同一个 backbone VLM，但用不同的 prompt 角色）综合这些输出和原始问题，给出最终答案

**示例答案**：执行完上面的示例程序后，render_egocentric() 生成的图片显示：从新视角看出去，毛绒玩具在前方偏左、且看起来比原图更大（更近了）。Reasoner 据此回答 "Yes, you will get closer."

---

### 4.3 关键设计决策

**为什么 DSL 程序而不是直接给 VLM 暴露工具？** 消融实验（Table 8, P.11）表明：直接暴露 DSL 原语给 VLM 而不加验证器，在 MindCube 上性能反而下降（GPT-5-mini: 58.0 → 53.2）。因为 VLM 会生成语义上奇怪的程序——比如先 query 物体的位置，然后变换视角，然后**仍然使用旧视角下查到的位置信息**，导致答案错误。AST 编译器堵死了这类视角状态不一致的错误。

**为什么用 3D 点云而不是生成新视角？** 对比方法 MindJourney 用视频生成模型模拟新视角，但生成结果缺乏几何一致性，在视频场景下反而降低精度（Table 6, VSI-Bench: -10.9）。3D 点云保证了几何精度，DSL 保证了对记忆的正确操作方式。

## 5. 实验

### 5.1 实验设置

- **三个 Benchmark**: MindCube-Tiny（多视图图像, 150 问题）、VSI-Bench-Tiny（静态视频, 400 问题）、VLM4D-Real（动态视频, 100 问题）
- **实现细节**: Pi3 重建，短边 378px，视频取 64 帧重建 + 16 帧 VLM。SAM3 阈值 0.65
- **Baselines**: GPT-5-mini / Gemini-3-flash 直接推理 + SpaceOM / Spatial-MLLM / SpatialLadder 专用模型 + MindJourney（视频生成视角变换）/ Think3D（3D 重建+无约束工具）

### 5.2 主要结果

**MindCube-Tiny**（Table 5）:
| Model | Baseline | Reasmory | Gain |
|-------|----------|----------|------|
| GPT-5-mini | 58.0 | 76.0 | +18.0 |
| Gemini-3-flash | 68.7 | 86.0 | +17.3 |

**VSI-Bench-Tiny**（Table 6）:
| Model | Baseline | Reasmory | Gain |
|-------|----------|----------|------|
| GPT-5-mini | 49.6 | 55.8 | +6.2 |
| Gemini-3-flash | 51.6 | 65.0 | +13.4 |

**VLM4D-Real**（Table 7）:
| Model | Baseline | Reasmory | Gain |
|-------|----------|----------|------|
| GPT-5-mini | 65.3 | 72.7 | +7.4 |
| Gemini-3-flash | 76.0 | 82.0 | +6.0 |

### 5.3 消融

关键消融（Table 8）: 只暴露空间原语而不加 DSL 验证 → GPT-5-mini 在 MindCube 上从 58.0 掉到 53.2。说明不加验证的 DSL 原语暴露反而有害。全量 DSL 验证器才是提升来源。

### 5.4 可能的不足

- 依赖重建和语义分割质量，严重遮挡或复杂场景会失败
- 动态场景提升幅度（+6-7.4%）小于多视图图像（+17-18%），时域复杂性仍是挑战
- 仅测了三个 Benchmark，未涉及室外大场景或具身任务
- 只测了 GPT-5-mini / Gemini-3-flash，未涉及开源 VLM

## 6. 一句话总结

Reasmory 通过构建显式 3D 空间记忆并引入带 AST 验证的 DSL 程序约束，将 VLM 空间推理从脆弱的自由工具调用转变为可靠的结构化程序执行，在多视图和视频空间推理基准上一致超越 GPT-5-mini 和 Gemini-3-flash 6-18%。
